# OpenBose deep research — NC 700, 23 September 2026

Status: **public-source research only**. No live NC 700, HCI trace, verified firmware binary analysis, unlocked codec, or hardware patch was used. This dossier supplements [RESEARCH.md](RESEARCH.md); [PLATFORM_FEASIBILITY.md](PLATFORM_FEASIBILITY.md), [CODEC_FEASIBILITY.md](CODEC_FEASIBILITY.md) and [PROTOCOL_CAPTURE_PLAN.md](PROTOCOL_CAPTURE_PLAN.md) contain implementation-specific evidence.

## Executive findings and corrections

1. **Silicon-level aptX evidence is positive, not merely hypothetical.** [Qualcomm's official Bluetooth speaker SoC product comparison](https://www.qualcomm.com/audio/applications/bluetooth-wireless-speakers/product-list) lists **CSRA68105** with **aptX Audio and aptX HD**. [Qualcomm's CSRA68105 product page](https://www.qualcomm.com/audio/products/csra68105) says its dual Kalimba audio DSPs can dynamically reconfigure, with downloadable capabilities from **RAM/QSPI** and preinstalled ROM libraries. [The 2018 Qualcomm product brief](https://docs.qualcomm.com/bundle/publicresource/87-CE933-1_REV_A_CSRA68105_Audio_SOC_Product_Brief.pdf) specifies two 240 MHz audio DSPs, **192 KB program RAM**, **512 KB data RAM**, a programmable 120 MHz application subsystem, and external QSPI flash support up to 256 Mb. These are **chip-platform features**, not evidence that Bose has included/licensed/enabled either codec or exposed a third-party RAM loader.
2. **The SoC identification is independently corroborated.** [52audio's NC 700 teardown](https://www.52audio.com/archives/31642.html) identifies a Qualcomm CSRA68105, separately from [iclemens/bose](https://github.com/iclemens/bose)'s hardware statement. Physical revisions should still be identified in a real-device baseline.
3. **Shipping headphone codec support is reported as SBC and AAC.** [SoundGuys' NC 700 review](https://www.soundguys.com/bose-noise-cancelling-headphones-700-24897/) reports only these two. Bose's current A2DP advertisements on **our actual headphones** must be captured rather than assumed from review text. Chipset support and product support are different layers.
4. **A directly relevant Android NC 700 control app exists:** [danielgjackson/noisecancel](https://github.com/danielgjackson/noisecancel) is not QC35-only. Its [README](https://github.com/danielgjackson/noisecancel/blob/master/README.md) and [SendService.kt](https://github.com/danielgjackson/noisecancel/blob/master/app/src/main/java/dev/danjackson/noisecancel/SendService.kt) show public Android SPP/RFCOMM connection, NC 700 ANC SETGET request, and response bytes. The app sends the same command three times (333 ms apart) because an off→on transition resets to the default level before a second level setting; do **not** blindly copy retries for every command.
5. **Windows implementation precedent exists:** [SaorCon](https://github.com/bosefirmware/SaorCon-Win-BT-QC35-NC700), particularly [SaorCon/BoseDevices.cs](https://github.com/bosefirmware/SaorCon-Win-BT-QC35-NC700/blob/main/SaorCon/BoseDevices.cs), implements a distinct NC 700 class, RFCOMM channel 8, battery and ANC. Its README discloses occasional C# RFCOMM **receive failures on Windows**, despite equivalent C++ sometimes working. Test Windows Bluetooth adapters and reconnect thoroughly.
6. **Firmware recovery must not be inferred from a generic Bose tool.** [bose-dfu](https://github.com/bosefirmware/bose-dfu/blob/main/README.md) explicitly excludes NC 700 for using a **different update protocol**, and [device_ids.rs](https://github.com/bosefirmware/bose-dfu/blob/main/src/device_ids.rs) lists USB PID **0x40fc** as incompatible. Do not use its enter-dfu/download/force operations on the NC 700.
7. **Bose's EQ persists on the headset.** [Bose's EQ support article](https://support.bose.com/s/article/nc700-headphonearn-adjusting-the-tone-controls-on-your-product---ka08c000001pxamaae?language=en_US) documents firmware **1.4.12+** and bass/mid/treble each **-10..+10**, step 1. [The official user manual](https://assets.bose.com/content/dam/Bose_DAM/Web/consumer_electronics/global/products/headphones/noise_cancelling_headphones_700_charging_case_pkg/pdf/support/842497_og_noise-cancelling-headphones-700%2Bcharging-case_ml.pdf) says prior EQ is retained when powering back on. Consequently a direct Bose EQ write is **persistent**, not temporary merely because OpenBose remains running.
8. **The OpenBose repo layout has been preserved:** [master](https://github.com/aeiouofficial/openBose/tree/master) contains documentation, [reference/original-bose-code](https://github.com/aeiouofficial/openBose/tree/reference/original-bose-code) preserves the original Python/USB/Wireshark code. Keep research/build work on named branches and import only reviewed pieces.

### Relevant protocol details

- NC 700 BMAP over classic Bluetooth RFCOMM **channel 8** reported in iclemens and SaorCon. [noisecancel's Android client](https://github.com/danielgjackson/noisecancel/blob/master/app/src/main/java/dev/danjackson/noisecancel/SendService.kt) uses public SPP UUID `00001101-0000-1000-8000-00805F9B34FB`; resolve SDP and verify our actual headset rather than hardcode speculative alternative UUIDs.
- BMAP unframed command: `[function-block, function-id, operator, payload-length, payload...]`. Standard operators in iclemens: `GET=1`, `SETGET=2`, `STATUS=3`, `ERROR=4`, `START=5`; other command responses may include result/processing. USB adds distinct envelope; do not feed it into Bluetooth parser.
- NC 700 ANC request documented by two unrelated repos: `01 05 02 02 [10-level] [enabled:0|1]`; response documented in noisecancel: `01 05 03 03 0b [10-level] [enabled]`. Its UI supports off/0/5/10, but protocol nominally has a 0..10 control range. Writes need firmware-specific readback tests.
- EQ read at BMAP **1.7**, `01 07`. The original Python USB prototype parses *nominally* 3 records [signed min, signed max, signed value, band index], but implementation has a slice bug. Do not call this schema verified on our actual firmware until the GET capture is checked. Bose officially supports -10..10 per band.
- Device identification: [Goodyear firmware index](https://github.com/bosefirmware/ced/blob/master/goodyear/index.xml) identifies product `0x4024`. The device's reported version/revision must be checked before any command registry allows a write.
- NC 700 OTA observations in iclemens use function block **3** and start/transfer commands; mark all block-3 writes and unrecognized blocks **DENIED** at application transport boundary by default.
- Android/Windows A2DP audio transfer and this RFCOMM control channel are **different Bluetooth profiles**; installing an Android/Windows app alone cannot install a new decoder into headphone firmware.

## Firmware archive and provenance cautions

- [Bose's official NC 700 update chronology](https://support.bose.com/s/article/noise-cancelling-headphones-700-updating-the-software-or-firmware-of-your-product?language=en_US) lists 1.4.12/1.5.1/1.7.0/1.8.2 and **2.0.4 manufacturing-only**. The GitHub archive ending at 1.8.2 is **not exhaustive** of every shipped firmware revision.
- 1.4.12 introduced adjustable EQ but Bose documented an error-state issue. 1.5.1 addressed red/white LED errors; 1.7.0 widened rollout and further addressed LED/VOIP issues. Changes in firmware affect the write-command compatibility matrix.
- The archive calls its binaries `encrypted_prod`. This filename and iclemens' phrase “supposedly encrypted” are not cryptographic proof. A complete container parser, entropy inspection, signature identification and key analysis **remain undone**.
- [Qualcomm's public product page](https://www.qualcomm.com/audio/products/csra68105) says fuller platform documentation requires a verified company account. An arbitrary codec DSP blob, callable loader or firmware signing method has **not** been obtained.

## What remains unverified

- Actual NC 700 AVDTP `GetCapabilities` and `SetConfiguration` for the specific device/firmware, particularly aptX Classic `4f/0001`, aptX HD `d7/0024`, LDAC `12d/00aa`.
- Whether Bose included aptX/HD decoder capabilities in ROM, external QSPI, disabled software packages or not at all.
- Whether NC 700 firmware exposes a safe **temporary RAM-download** control path to the owner, or whether available loaders are signed/privileged.
- Whether codec activation would have enough memory and CPU headroom **alongside Bose ANC/beamforming/multipoint**, even if silicon supports it.
- Whether any user-available and **tested** rollback/recovery path exists after firmware corruption. Generic `bose-dfu` is not it.
- Actual Windows/Android adapter and OS/driver behavior; system-wide EQ support per platform; official-app concurrency.

## Decisions for app planning

Separate product capabilities into **Headphone settings** (persistent), **Host EQ** (only while active and only where platform routing permits), **Codec laboratory** (read-only discovery, evidence, offline research) and **Conditional advanced experiments** (off by default and blocked without recovery proof). Do not advertise the Qualcomm platform's aptX/HD support as already enabled on NC 700.
